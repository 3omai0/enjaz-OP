# Setup and operations

## Local installation
Install Node.js 22 and npm. Open this repository directory and run:

```sh
npm ci
npm run setup
npm run dev
```

Open http://localhost:3100/setup. Enter your name, email, password (at least 8 characters) and confirmation. This creates the first administrator and closes setup. There are no default credentials. Add employees through Team, ask them to change temporary passwords, create a project and select its members.

Setup creates .env with random session and cron secrets without overwriting an existing file. With DATABASE_URL empty, PGlite creates and migrates .data/pglite automatically. Only one process may use that local directory. Stop the server before running database utilities. Production requires Neon.

## Neon database
Create an account at https://neon.com, create a project and a dedicated database, then choose Connect and copy the pooled connection string. Put it in DATABASE_URL in .env, preserving SSL options. Stop the server and run `npm run db:migrate`, then restart. Visit /setup to create the administrator in the new database. Switching connections does not transfer local data. The application uses Neon's HTTP driver; arbitrary PostgreSQL servers are not supported automatically.

## Configuration
- AUTH_SECRET: required random secret of at least 32 characters; generated by setup.
- DATABASE_URL: empty for local development, Neon connection string required for production.
- CRON_SECRET: generated by setup; configure the scheduler with the same value.
- VAPID_PUBLIC_KEY and VAPID_PRIVATE_KEY: optional device push keys.
- VAPID_SUBJECT: a real contact such as mailto:you@your-domain.example when enabling push.
- NEXT_PUBLIC_APP_TIMEZONE: IANA timezone, defaults to Asia/Riyadh; set before building.
- SEED_ADMIN_NAME, SEED_ADMIN_EMAIL, SEED_ADMIN_PASSWORD: optional demo seeding only.

Never commit .env or database files. Use independent secrets per installation. Changing AUTH_SECRET invalidates sessions.

## Deploy
Import a separate GitHub repository into Vercel using Next.js and Node.js 22. Configure DATABASE_URL and AUTH_SECRET, CRON_SECRET for recurring tasks, and optional VAPID settings. Use a separate database for previews. Apply migrations against the intended production database before deploying changes that need them. Protect the initial deployment with hosting access controls until you create the administrator at /setup: the first visitor to an empty installation can claim it.

vercel.json requests a cron call every minute. Confirm your hosting plan supports that frequency. Otherwise remove the crons property and configure an external scheduler.

For a persistent Node server, configure .env, run `npm ci`, `npm run db:migrate`, `npm run build`, then `npm run start`. It listens on port 3100. Provide HTTPS through a reverse proxy and manage the process with your service manager. Production session cookies require HTTPS. Fonts use the system font stack with no external downloads.

## Recurring tasks
Call GET https://YOUR-DOMAIN.example/api/cron/recurring every minute with `Authorization: Bearer YOUR_CRON_SECRET` or an `x-cron-secret` header. Keep the secret out of URLs. Vercel Cron supplies the bearer token from CRON_SECRET. Create a schedule in the UI and verify the task appears at its due time. Occurrences overdue by more than a day are skipped.

## Device push
Run `npx web-push generate-vapid-keys`, save both keys in the environment and set VAPID_SUBJECT to your real contact address. Restart or redeploy. Keep keys stable; rotating them requires devices to subscribe again. Enable notifications in Settings and send a test. Deployed sites require HTTPS and browser permission; some devices require installing the web app to the home screen. In-app notifications work without VAPID.

## Demo and recovery
On an empty database only, stop the local server and run `npm run db:seed`. It creates fictional example.com users and sample projects. Generated passwords print once. Do not seed a real team workspace or seed before using /setup.

With administrative server access and the correct .env, run `npm run reset-password -- admin@your-domain.example` and follow the hidden password prompt. Omit the email only when there is a single administrator. Resetting signs that user out everywhere.

## Backups and upgrades
Back up Neon using your provider's export/recovery tools before migrations and test restoration separately. For local PGlite, stop all processes before copying the entire .data directory. Store secrets securely outside Git. To upgrade, review changes, run npm ci, apply db:migrate, lint, typecheck, build and redeploy. Use migration history in production, not db:push.

## Publish to GitHub
Create an empty public repository, open this directory and run:

```sh
git init
git add .
git status
git commit -m "Initial open-source release"
git branch -M main
git remote add origin https://github.com/3omai0/enjaz-OP.git
git push -u origin main
```

Before committing, check that .env, .data and dependency/build directories are absent. Never copy another project's .git history. MIT permits use, modification and distribution subject to its notice requirements. CI lints and builds pushes and pull requests.

## Troubleshooting
Missing AUTH_SECRET: run setup if .env does not exist; otherwise generate a secret with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and edit the file. Closed setup means users already exist; use login or password recovery. Neon errors: check the connection, network and migrations. PGlite locks: stop other processes. Port conflicts: use `npm run dev -- --port 3101`. Missing recurring tasks: inspect scheduler calls, authentication and timezone. Run npm run lint, npm run typecheck and npm run build to check code independently.

## VPS hosting
